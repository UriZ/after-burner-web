## A2 — one line in `player.js` to put the night pose sheet into service

**Owner: player-feel.** `src/render/spriteFactory.js` now exports `JET_POSE_SHEET_NIGHT`
(`player-f14-night.png`, same 9 poses, same geometry as the day sheet — the night sheet is
generated by the same function with the night palette, so they cannot drift). It is correct
and measured (JET-SIL: two-blade 100%, fin extent 38.4%, nozzle sep 30.3%, cant 1.22, aspect
3.09 — all in band) but nothing selects it.

`Player.update()` currently reads:

```js
const usedSheet = !this._night && selectPoseCell(this.sprite, this._poseTexture, JET_POSE_SHEET, -poseDeg);
```

The `!this._night` guard exists because there was no night sheet. There is one now. The
change is to load both and pick by `this._night`:

```js
// in the constructor, alongside the existing load
loadPoseSheetTexture(JET_POSE_SHEET_NIGHT).then((tex) => { this._poseTextureNight = tex; });

// in update()
const sheetTex = this._night ? this._poseTextureNight : this._poseTexture;
const sheet = this._night ? JET_POSE_SHEET_NIGHT : JET_POSE_SHEET;
const usedSheet = selectPoseCell(this.sprite, sheetTex, sheet, -poseDeg);
if (!usedSheet) this.sprite.material.rotation = -THREE.MathUtils.degToRad(poseDeg);
```

`selectPoseCell` already returns `false` on a null texture, so the procedural fallback holds
unchanged if either sheet fails to decode. `setJetNightPalette` stays as the fallback's
palette swap. Say the word and I will not touch `player.js` either way — it is yours.

Note for whoever does it: the sprite quad's aspect changed this round (`JET_H` 31 → 72, the
sheet cell matches at 100×72). `_origScaleX/_origScaleY` pick it up automatically; the jet's
on-screen size and position are unchanged (verified on a capture) because `worldHeight`
tracks `JET_H`. Nothing in `player.js` needs editing for that part.

## A4 — for criteria-fix: two criteria defects found this round

**(a) R4 gap 1 criterion (c), "no single feature occupying >12% of silhouette area", fails
every real aeroplane as literally written.** Under the obvious operator (largest 8-connected
single-colour component) a *wing* is a feature, and a wing is 22–28% of any aircraft sprite's
area — including the arcade's. The defect the criterion exists to catch is a MARK (the
black-rimmed red disc), not a structural member. `tools/art/enemysil.py` gates on the largest
**compact** component instead (bbox aspect ≤3:1 both ways, ≥50% bbox fill) and prints the
naive number alongside. Suggest REFERENCE.md adopt that wording.

**(b) The same criterion family's "leading edge rising ≥15°" needs its sign named.** A
head-on aircraft's leading edge rises inboard→outboard; a rear-aspect one's rises outboard.
Measured with a signed convention the rear aspect reads negative and looks like a failure when
it is not. The gate should be |angle|.

**(c) JET-SIL's 250 px validity floor is real and should be stated as a gate, not a note.**
REFERENCE.md mentions in passing that below ~250 px of jet span "the blades are not resolvable
and the operator is meaningless". It is stronger than a note: measured on the SAME committed
sheet, fin-pair extent reads **100.0% of SPAN** from the 100 px authored cell and **36.4%**
from the 330 px in-game render, because at 100 px the fin band is ~7 rows and the 0.30·S
wing-onset row lands in a different place. Anyone validating a sprite against the authored PNG
instead of a capture will get a number that is not merely imprecise but wrong by 3×. Suggest
REFERENCE.md make "span >= 250 px in the measured image" a precondition of the operator rather
than a parenthetical.

**(d) I8, resolved on evidence.** The published jet centroid and the judge's differ because
they are two operators on one mask: on this build's stage-1 frame the jet-on/jet-off
difference mask gives **57.51%H as a pixel centroid** and **55.06%H as a bbox centre**, a
2.45-point gap that matches the "2–3 points optimistic" history. The 52–60%H band was drawn
against the judge's pixel centroid, so REFERENCE.md should say "mean y of the jet-on/jet-off
difference mask's largest 8-connected component" and the authoring-side figure should be
recomputed that way.

## A5 — barrel-roll sheet is shipped; `player.js` must drop BOTH its rotation and its squish

**Owner: player-feel.** `src/assets/sprites/player-f14-roll.png` exists — 8 drawn frames of a
full 360° roll, generated by `tools/art/sheets/player-f14-roll.js`, same 100×72 cell and same
quad as `JET_POSE_SHEET`, so nothing about the sprite's scale changes when the roll starts.
`spriteFactory.js` exports:

```js
export const JET_ROLL_SHEET;                                   // {url, cols: 8, cellWidth, cellHeight}
export function selectRollCell(sprite, sheetTexture, rollPhase, sheet = JET_ROLL_SHEET);
```

`rollPhase` is the 0..1 field you already expose; `selectRollCell` wraps it, so 1.0 lands back
on cell 0. It returns `false` on a null texture, so your current path stays as the fallback —
same contract as `selectPoseCell`.

**The one thing that will go wrong if it is wired naively.** Both the rotation and the span
squish are **baked into the art**. `selectRollCell` clears `material.rotation` itself, but the
scale is yours:

```js
// player.js, in the barrel-roll branch — REMOVE these two lines when the sheet is in force
const squish = Math.max(0.15, Math.abs(Math.cos(angle)));
this.sprite.scale.set(this._origScaleX * squish, this._origScaleY, 1);
```

Leave them in and the squeeze applies twice — the jet goes to ~9% span at the quarter points
instead of 30%. Keep them only on the `selectRollCell === false` fallback path.

**Why it is worth doing beyond "one less spun bitmap":** the arcade's roll is not the astern
aircraft rotated. `reference/stage4-barrel-roll-t222.png` shows the **dorsal** surface in a
blue-violet family that appears nowhere in the astern view — measured ladder `#232d4d /
#525f8b / #6474a1 / #6d7faf / #8f9fcf` (airframe box x[412,707] y[333,463], hue 200–300° ∧
S>0.08, 10 802 px, value-band means over quintiles). A spun astern bitmap stays warm grey for
the whole manoeuvre and is wrong at every phase except zero. The sheet crossfades ventral →
dorsal with `(1 - cos θ)/2`, so frame 0 is the familiar aircraft and frame 4 is t222's blue.

8 frames rather than the art-critique §4 inventory's 6, deliberately: at 45° steps all four
structurally distinct phases — astern, edge-on, inverted dorsal, edge-on — land exactly on a
frame. At 60° steps neither edge-on moment does, so GAME_SPEC §1's "sprite narrows to a line"
would never actually be drawn.

**One limitation you should know before wiring it.** The two edge-on cells go invisible under
NearestFilter point sampling at a **7 px quad** (`tools/art/sheet_visibility.py`). That is the
R3 disappearing-aircraft failure mode, and raising the span floor does not fix it — the cause
is that a 100×72 cell holding a 31-row aircraft puts two of the three sampled texel rows in
transparent padding at that size. It does not bite today: the player jet measures **115 native
px** in level flight and nothing in the tree scales it below 1.0 except the very squish being
removed. I have set the player sheets' check range to 24–160 px and written the reasoning into
the script rather than quietly widening a band. **If anything ever renders the player jet below
~24 native px, tell me and I will re-cut the roll cell tighter.**

## A7 — a `?nosheet=1` flag would close the last unverifiable path (owner: lead, for the param table)

The procedural textures in `spriteFactory.js` are the fallback if an authored sheet fails to
decode. That path **cannot be exercised from outside**: `poseSource` reads `sheet-day` even at
tick 1, so there is no tick early enough to catch the pre-decode state, and nothing else forces
a null texture.

That is exactly why `PLAYER_PALETTE_NIGHT` drifted to a different set of blue-greys and a
daylight-orange afterburner without anyone noticing (r5d, criteria-fix's find). I have fixed the
table and verified it as a source-level equality against the shipped PNGs, but **the render path
itself is still unverified**, and the next drift will be just as silent.

A one-line measurement-only flag in `spriteFactory.js`'s `loadPoseSheetTexture` — resolve `null`
when `?nosheet=1` is set — would make the fallback capturable, and the existing
`isolate_jet.py` + `jetsil.py` pair would then cover it the same way they cover the sheets.
It is my file, so I will add it on request; I have not, because it adds a param to a table the
lead owns and the round is closing.
